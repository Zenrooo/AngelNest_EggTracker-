# Future Supabase integration

The current UI is a single-browser demonstration. `frontend/src/storage.js` owns persistence; `domain.js` defines the demo's validation rules. The event history is an implementation detail of the prototype, not a proposed PostgreSQL table or a deployed schema.

## Review before implementation

The latest project brief names Employee, Egg_Size, Production, Production_Detail, Inventory, Customer, Sale, Sale_Detail, Expense_Category, and Expense. Compare the actual approved ERD, data dictionary, and logical model with the Software Engineering tray-management workflow. Decide how packing is recorded and how Employee relates to Supabase Auth. Do not infer that an earlier draft or this local demo is the approved schema.

## Replace demo storage in small steps

1. Agree on production and packing fields, supported units, role permissions, and how corrections will be recorded.
2. Create reviewed migrations for the approved design. No migrations were generated by this prototype.
3. Configure a development Supabase project and verify a real read/write operation using disposable development data.
4. Add Supabase Auth and verify the user's token and permissions for every protected operation.
5. Define an API contract. Replace synchronous local persistence with asynchronous, authorized API calls and loading/error states. Never treat the browser's totals as authoritative.
6. Enforce production validation and stock constraints in PostgreSQL/server operations. Packing and sales must check and update stock atomically, with protection against concurrent overselling and duplicate requests.
7. If the browser accesses Supabase directly, enable RLS and test policies for each role. Privileged keys stay server-side and require explicit server authorization.
8. Test the first production-to-inventory workflow before integrating packing and sales. Confirm totals after reload and across separate authenticated sessions.

The root `.env.example` already has placeholders. Vite exposes variables prefixed `VITE_` to the browser: never add a privileged key under that prefix. The demo reads no credentials and does not call the existing health API. The health endpoint only establishes API availability.

## Current limitations

- Authentication and role-based access control are not implemented.
- Demo data is local to an origin (scheme, hostname, and port) and browser profile. `localhost` and `127.0.0.1` can have different demo records. Clearing browser storage removes demo records.
- Transactions apply in the order saved. Dates are record labels; backdated entries do not create historical inventory snapshots.
- A stale-tab warning reduces accidental overwrites but localStorage is not a transactional multi-user database.
- The demo provides add/history flows and reset. Record correction, refunds, and audit requirements need a reviewed design before implementation.
- Simple net result is sales revenue minus recorded expenses, not a full accounting profit calculation.
